# Optional External Dependencies of Built-in Modules (Module Level Dependency Aggregation)

This page explains how SDK built-in modules can declare external components
"only fetched when the module participates in the build", and how this
mechanism takes effect during project install/build. It serves both as a
design explanation and as an authoring/convention reference for module
maintainers.

## Background and Motivation

`sf-pkg` (`tools/sdk_py_actions/sf_pkg_ext.py`) is a wrapper around Conan 2:

- External dependencies are declared in the project root `conanfile.py`
  (generated by `sf-pkg init`);
- `sf-pkg install` is equivalent to
  `conan install . --output-folder=sf-pkgs --deployer=full_deploy`, deploying
  the package sources together with the generated
  `sf-pkgs/Kconfig.conandeps` and `sf-pkgs/SConscript_conandeps`;
- The build side (`tools/build/building.py`) only consumes what is already
  deployed under `sf-pkgs/` (`AddExternalComponents`, Kconfig `osource`); it
  never triggers conan itself.

Pain point: external components needed by SDK built-in modules (e.g.
`middleware/*`, `customer/peripherals/*`) could only be declared centrally in
the project root `conanfile.py`, so they were fetched/exposed even when the
module was not compiled, and project developers had to maintain dependencies
on behalf of SDK modules.

## Goals and Constraints

1. Resolution: **single graph aggregation** - all module dependencies are
   merged into one consumer conanfile and installed with a single
   `conan install`; Conan performs unified version resolution/dedup.
2. Participation: **static config resolution** - read the resolved `.config`
   of the current build, not evaluated at SCons runtime.
3. Granularity: **per module enable symbol** - a module's dependencies are
   merged only when its enable symbol is `y`.
4. Compile gating: **module Kconfig `select`s the package symbol** - the
   fetch layer only guarantees package sources land in `sf-pkgs/`; whether a
   package is actually compiled is decided by the module Kconfig (decoupled).
5. Trigger: **automatically at the build entry** (board known, `.config`
   resolved); standalone `sf-pkg install` remains and supports `--board`.

## Project Root Declaration Switched to YAML

The project root dependency declaration moves from `conanfile.py` to
`sf-pkg.yaml`:

```yaml
# Project root fixed dependencies
requires:
  - sht30/0.0.4@caisong123
support_sdk_version: "^2.4"   # optional: SDK range (npm semver), unchecked when absent
```

- YAML is chosen over JSON: it supports comments and avoids error-prone syntax
  (trailing commas/quotes); both project developers and module authors can
  read and edit it.
- It shares the schema with module manifests (`requires` /
  `support_sdk_version`); the project root has no `enable` and is treated as a
  project-level fixed dependency.
- Conan does not understand YAML: before fetching, `sf-pkg` merges "project
  root requires + matched module requires" into a standard consumer
  conanfile. The base is produced by the official `conan new sf-pkg-project`
  template (kept up to date with the conan config bundle); the SDK only
  injects the requires list into it. The result lives at
  `.sf-pkg/conanfile.py` (gitignored) and is passed to
  `conan install`.
- Benefit: aggregation becomes plain data merging - no need to import/inherit
  an arbitrary user python recipe; the hand-edited `conanfile.py` user entry
  disappears.
- Escape hatch: if a project genuinely needs python-level capabilities
  (conditional requirements, `tool_requires`, complex conf), "advanced mode"
  is kept - when the project root has a `conanfile.py` and no `sf-pkg.yaml`,
  `sf-pkg install` runs `conan install` on it directly (legacy behavior) and
  module-level dependencies do not participate. `sf-pkg init` only generates
  `sf-pkg.yaml`; old projects without that file fall back to legacy behavior
  with no breaking migration.

## Module Dependency Manifest

Every SDK built-in module that needs external components carries a local
`sf-pkg.yaml` placed **in the same directory as the Kconfig that defines the
module enable symbol**:

```yaml
# sf-pkg external components needed when this module takes part in the build
enable:
  - SF32LB5XX_MOD_ENABLE   # Kconfig enable symbol; any 'y' means "participates"
requires:
  - mesh-lib/1.3.0@acme    # conan reference; version ranges allowed
  - crypto/2.0.1@sifli
support_sdk_version: "^2.4"   # optional: SDK range this module needs (npm semver)
```

Fields:

- `enable`: Kconfig enable symbols of this module. If any listed symbol is `y`
  the module is considered participating; if the field is absent/empty the
  module is treated as "always participating" (only for fixed modules that
  have no switch).
- `requires`: same Conan reference format as the project root.
- `support_sdk_version`: npm-style semver range (e.g. `^2.4`, `~2.4.1`,
  `>=2.4,<3`). Semantics match the package recipe class attribute
  `support_sdk_version` and the base class
  `sf-pkg-base.SourceOnlyBase.validate()`: parsed with
  `semantic_version.NpmSpec`, and the SDK version comes from the environment
  variable `SIFLI_SDK_VERSION` (set by `export.ps1` / `set_env.bat`, e.g.
  `2.4` / `2.4.1`).

### Candidate Module Discovery: Based on `kconfiglist`, No Full Scan

Every build's `InitBuild` writes the full list of Kconfig files actually
parsed for the current board (absolute paths, deduplicated, gated by the
chip/board config tree) into `build_dir/kconfiglist`. Hence:

> Candidate manifests = for each directory of a file in `kconfiglist`, check
> whether a sibling `sf-pkg.yaml` exists.

- Cost is O(number of Kconfig files parsed), no recursion, no full traversal.
- Modules outside the current chip/board tree (other chip families,
  unsourced subtrees, docs/tools, ...) never appear in `kconfiglist`, which
  naturally aligns discovery with the SConscript/Kconfig tree.
- If a family of modules has its enable symbols defined in a shared/upper
  aggregator Kconfig (e.g. `drivers/hal/Kconfig` defines many switches while
  sources live in subdirectories), one manifest placed next to that
  aggregator Kconfig - listing the symbols under `enable` - covers all of its
  sub-modules; no source-tree scan is needed.

### SDK Version Check

Instead of the legacy conan hook / `required_sdk_version` mechanism, the SDK
**replicates** the `SourceOnlyBase.validate()` logic:

1. Read `SIFLI_SDK_VERSION`; if any `support_sdk_version` is declared but the
   variable is missing, or the version is not a valid semver, fail with a
   clear error.
2. `semantic_version.Version.coerce(sdk_ver)` parses the actual version.
3. `semantic_version.NpmSpec(range)` parses the declared range; if
   `sdk_version not in spec`, fail naming the source file and the required vs
   actual versions.

The project root and **each enabled module** are validated SDK-side, before
any network/install action. Each **package**'s own `support_sdk_version` is
still validated by `sf-pkg-base.SourceOnlyBase.validate()` while Conan
resolves it; this layer does not repeat that.

## Data Flow

```
scons --board=<b>
  └─ PrepareEnv
      ├─ LoadRtconfig / InitBuild(#1)          generates build_dir/{.config,rtconfig.h,kconfiglist}
      ├─ BuildOptionUpdate(BuildOptions)
      ├─ EnsureSfPkgDepsForBoard(b)
      │    ├─ manifests_from_kconfiglist(kconfiglist)        → candidate module manifests
      │    ├─ load_root_manifest(project)                    → project root requires
      │    ├─ collect_requires(enabled modules)              → module requires
      │    ├─ check_sdk_versions(...)                        → fail on mismatch
      │    ├─ fingerprint(merged_requires, sdk_ver)
      │    ├─ same as .sf-pkg/installed.fingerprint? → return
      │    └─ different:
      │         wipe project/sf-pkgs/                         avoid stale packages
      │         generate_consumer_conanfile() → .sf-pkg/conanfile.py
      │         conan install <consumer>                      deploy into sf-pkgs/
      │         write .sf-pkg/installed.fingerprint
      │         InitBuild(#2) + BuildOptionUpdate             package Kconfigs present, module selects take effect
      └─ normal SConscript build (reads sf-pkgs/SConscript_conandeps)
```

- The fingerprint includes the SDK version: an SDK upgrade triggers a fresh
  resolve/reinstall even if the ranges did not change, so stale Conan range
  resolution is avoided.
- When there is no `sf-pkg.yaml` / no matched module, or in "advanced mode",
  everything is skipped, keeping offline and backward compatibility.
- `SIFLI_SF_PKG_OFFLINE=1` (or an equivalent switch) skips automatic
  fetching, for CI/offline use.

## Module Kconfig Compile Gating (Module Author Convention)

The fetch layer only guarantees package sources are present in `sf-pkgs/`;
whether a package is actually compiled is decided by the module's own Kconfig,
which `select`s the package's enable symbol declared in `Kconfig.conandeps`
(symbol names are a package-author contract; module authors follow the package
documentation). In the Kconfig tree module symbols are parsed first and the
package symbols are merged later via `osource sf-pkgs/Kconfig.conandeps`;
kconfiglib indexes symbols by name so later definitions merge into earlier
references, letting `select` work across files.

## Deliverables

- `tools/sdk_py_actions/sf_pkg_deps.py`: core collection/aggregation/consumer
  generation/validation logic, reused by `building.py` and `sf_pkg_ext.py`.
- `tools/build/building.py`: `EnsureSfPkgDepsForBoard` inserted into
  `PrepareEnv`, with a second `InitBuild` when needed.
- `tools/sdk_py_actions/sf_pkg_ext.py`: `init` generates `sf-pkg.yaml`;
  `install` supports `--board`; shared conan command extracted.
- Project root `sf-pkg.yaml` template (generated by `sf-pkg init`).
- `.gitignore` entries for `.sf-pkg/` and `sf-pkgs/`.

## Verification

1. Building a regular project without external dependencies behaves unchanged
   (no `sf-pkg.yaml` / empty aggregation → skipped).
2. `sf-pkg init` generates `sf-pkg.yaml`; `sf-pkg install` deploys `sf-pkgs/`
   correctly in YAML mode.
3. Minimal experiment: place a test module manifest in a project whose
   `requires` points to a known small package on the registry → after a
   build, the package appears in `sf-pkgs/`, `Kconfig.conandeps` /
   `SConscript_conandeps` are generated, and the module Kconfig `select`ed
   package symbol is `y`.
4. Disable that module's enable symbol and rebuild → the fingerprint change
   triggers a reinstall, the package is removed from `sf-pkgs/` and no longer
   linked.
5. No network / `SIFLI_SF_PKG_OFFLINE=1` → build proceeds, fetching skipped.
6. Legacy projects (only `conanfile.py`) keep the advanced mode, identical to
   the old behavior.
7. SDK version check: declaring a `support_sdk_version` not satisfied by the
   current `SIFLI_SDK_VERSION` in the project root or an enabled module fails
   before any network action, naming the source file.
